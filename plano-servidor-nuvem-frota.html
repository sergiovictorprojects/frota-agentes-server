Plano de arquitetura · Frota de Agentes

Automação independente na nuvem

Como sair de "roda no computador do usuário via tarefa agendada" para "roda 24/7 num servidor próprio, com agentes reais e camadas de segurança" — sem quebrar os 6 artifacts já publicados.

Railway (recomendado) Postgres como fonte da verdade Claude Agent SDK MCP + OAuth US$ 25–55/mês

Resumo executivo

Três constatações reorganizam o desenho inteiro:

(a) O agendador resolve o problema — o connector MCP não. Um MCP server só executa quando alguém chama uma tool; ele não "roda sozinho". A independência vem de um processo com relógio próprio, de pé 24/7. O connector é só a janela pela qual os artifacts voltam a ver o estado.

(b) O banco dos artifacts deixa de ser fonte da verdade. ArtifactData só existe dentro de uma sessão Claude Code; um servidor na nuvem não alcança aquele banco, e a CSP do artifact bloqueia o caminho inverso. O servidor precisa do próprio Postgres — não é preferência, é consequência da plataforma.

(c) Existe uma lacuna que nenhuma arquitetura resolve sozinha: publicar Claude Artifacts. Hoje a automação publica um artifact novo como entrega. Não há API pública para um servidor terceiro criar um Claude Artifact. Essa é a decisão de produto mais importante do plano — ver decisão D4.

Recomendação em uma linha: um container único em Railway (ou Fly.io em São Paulo), Node/TypeScript, Postgres como fonte da verdade, agendamento interno via pg-boss, loop agentico via Claude Agent SDK com papéis próprios (frota:*), e um MCP server Streamable HTTP com OAuth restrito a uma única conta. Custo típico: US$ 25–55/mês.

A seta do relógio interno para o orchestrator não passa por claude.ai nem pelo computador do usuário — é isso, e só isso, que resolve o problema original.

Decisão de dados

Postgres próprio como fonte da verdade; os artifacts viram clientes de leitura via tools MCP, com o db de cada artifact rebaixado a cache local da última leitura (degradação graciosa quando o connector não está presente). O schema lógico não muda — titulo, categoria, entregaUrl, metricas.indiceGeral etc. continuam idênticos na fronteira da API, então o JS dos artifacts troca a origem dos dados, não o formato.

A alternativa — manter o banco dos artifacts como fonte da verdade — foi descartada: não há API pública para um servidor terceiro escrever nesse banco, e a CSP bloqueia o caminho inverso.

Reproduzindo os agentes reais fora do Claude Code

Os subagent_type de hoje (ecc:architect, ecc:code-reviewer...) só existem dentro do Claude Code do usuário. O servidor usa o Claude Agent SDK com um registry próprio de 19 papéis (frota:architect, frota:code-reviewer...), cada um com prompt de sistema, a regra de conduta copiada literalmente do SKILL.md atual, e as tools que aquele papel pode usar — inclusive como controle real: d2 (Pesquisa) não recebe nenhuma tool de escrita porque é read-only por regra, e "gestores" nunca recebe tools de produção de entrega porque "nunca implementa direto".

O campo agente nos checkpoints passa a ser preenchido pelo código do orquestrador (que sabe qual papel realmente rodou), nunca pelo texto do modelo — honra a regra do SKILL.md de nunca atribuir trabalho a um agente que não foi de fato invocado.

Segurança

  • OAuth 2.1 via provedor que o usuário já tem (Google/GitHub) + allowlist de uma única conta — qualquer outra identidade recebe 403 antes de qualquer tool.
  • Validação de audience obrigatória no token (defesa contra confused deputy); nunca repassar o token recebido adiante.
  • Segredos só no cofre do provedor; boot falha rápido se faltar algum; API key da Anthropic dedicada com teto de gasto no console.
  • Rate limit em dois níveis: por token/IP nas tools MCP, e internamente — máx. 3 demandas/run, teto de gasto mensal com kill-switch automático que pausa a frota e notifica.
  • Contenção de prompt injection: conteúdo de demandas nunca entra em system prompt, cada papel só tem as tools do seu escopo, egress de rede restrito a api.anthropic.com, saídas de controle (status, contagem de violações) são structured output validado por schema — nunca texto livre interpretado.
  • Auditoria append-only de toda chamada MCP e ação do scheduler; Postgres sem porta pública; backup com restauração testada ao menos uma vez.

Decisões que só você pode tomar

Nada disso deveria começar a virar código antes de D1–D4 estarem fechadas.

D1 · Provedor de nuvem

Railway (mais simples) ou Fly.io em GRU/São Paulo (mais controle, dados no Brasil)?

Recomendação: Railway

D2 · Orçamento mensal

Vira o teto configurado no console da Anthropic e o kill-switch no código — sem esse número a Fase 1 não deveria começar.

Sugestão de partida: US$ 50/mês, alertas em 50/80/100%

D3 · Postgres como fonte da verdade

Aceita que o estado "real" da frota passe a viver fora do claude.ai, com o banco dos artifacts virando cache?

É a recomendação — na prática não há alternativa viável

D4 · Como tratar entregas (sem poder publicar Claude Artifacts)

(a) Servidor hospeda o HTML no próprio domínio — 100% automático, mas deixa de ser um Claude Artifact.
(b) Servidor gera e guarda; você pede no chat "publica a entrega pendente" — mantém como artifact, custa um passo humano.
(c) Híbrido: sempre auto-hospeda (fecha sozinho) + oferece promoção a artifact quando você quiser.

Recomendação: (c) híbrido

D5 · Nomes de agente mudam de ecc:* para frota:*

Exigência da própria regra de honestidade do SKILL.md — cria descontinuidade cosmética com relatórios históricos.

D6 · Republicar os 6 artifacts com connector

Risco de órfão de banco (já aconteceu antes). Alternativa: manter artifacts congelados e usar só a UI própria do servidor — perde a cidade 3D.

Recomendação: republicar, em etapas, com piloto de baixo risco primeiro

D7 · Canal de notificação

Telegram (mais rico, exige criar um bot) ou email (mais simples)?

D8 · Domínio próprio

Recomendado — ~US$ 12/ano — evita reregistrar o connector se trocar de provedor depois.

D9 · Frequência do agendador

Como fila vazia passa a custar zero, dá para rodar a cada 10 min em vez de 30 sem impacto de custo — melhora a latência percebida.

D10 · Residência de dados

Demandas podem conter material de terceiros — influencia D1 (Fly GRU mantém tudo no Brasil).

Plano de fases

Fase 0 — Decisões e provisionamentobloqueia tudo
  1. Fechar D1–D10 com você antes de qualquer código.
  2. Provisionar provedor, Postgres, domínio, API key dedicada com teto de gasto, OAuth, canal de notificação.
  3. Spike de 2h confirmando que não existe superfície HTTP sancionada para escrever no db de um artifact de fora.
  4. Fixar IDs de modelo e preços vigentes.
Fase 1 — MVP: independência real

Entrega: a fila é processada 24/7 com o computador desligado. Passe único, sem decomposição multi-agente ainda.

  1. Esqueleto + validação de segredos no boot
  2. Schema e migrações Postgres
  3. Repositórios com claim transacional (SKIP LOCKED)
  4. Cliente Anthropic com contabilidade e teto alto risco
  5. Orquestrador de passe único reproduzindo os passos 1–4 do SKILL.md
  6. Auditoria de métricas com structured output
  7. Scheduler pg-boss — encerra sem chamar o modelo se fila vazia
  8. UI web própria (criar demanda, ver fila, timeline, relatórios)
  9. Notificação (Telegram/email)
  10. Migração dos dados legados (export via Claude Code → import validado)
  11. Deploy + healthcheck + watchdog + backup testado
Fase 2 — MCP server e connector
  1. Módulo de tools compartilhado (in-process para o agente + HTTP para o connector)
  2. Streamable HTTP + OAuth + allowlist + validação de audience fronteira de segurança
  3. Rate limiting e audit log nas chamadas MCP
  4. Registro do connector na conta claude.ai + teste de handshake real
  5. Validação: operar a frota inteira pelo chat, sem abrir nenhum artifact
Fase 3 — Paridade comportamental (multi-agente)
  1. Registry dos 19 papéis frota:* com regras do SKILL.md como permissões reais de tools
  2. Triagem de complexidade (nível 1–4) decidindo passe único vs. decomposição
  3. Decomposição sequencial via subagents do Agent SDK
  4. Checkpoints e handoffs com agente preenchido pelo código
  5. Relatório com cadeia real de papéis invocados
  6. Suite de evals contra demandas douradas (baseline: Teste 01, índice 93)

Só aqui a tarefa local frota-processar-fila é desligada — nunca em paralelo com o servidor sobre bases diferentes.

Fase 4 — Artifacts republicados
  1. Piloto com 1 artifact de baixo risco (sugestão: Painel Geral) risco R1
  2. Trocar window.claude.db por tools MCP, db local vira cache com selo "sem conexão"
  3. Operação (o mais complexo — Kanban, Análises, Status, Detalhes)
  4. Conector de Inteligência com handoffs por polling (ritmo ajustado, não streaming real)
  5. Demais artifacts (Organograma, Código de Conduta, Sistema Organizacional)
Fase 5 — Entregas
  1. Geração e hospedagem de entrega seguindo o design system da frota
  2. Tool promover_entrega para publicação assistida como Claude Artifact
  3. Estados Aguardando humano / Aguardando insumo com notificação dedicada
Fase 6 — Endurecimento
  1. Observabilidade: métricas de run, custo por demanda
  2. Teste real de restauração de backup
  3. Ensaio de rotação de segredos
  4. Revisão de segurança dedicada sobre a superfície MCP/OAuth
  5. Runbook de falhas (run falha, teto trava, connector para de autenticar)

Critérios de sucesso

  • Demanda processada de ponta a ponta com o computador desligado
  • Run com fila vazia não gera nenhuma chamada ao modelo
  • Duas runs concorrentes nunca processam a mesma demanda
  • Connector MCP autenticado por OAuth, allowlist de uma conta
  • Teto de gasto pausa a frota automaticamente e notifica
  • Campo agente sempre corresponde a um papel realmente invocado
  • Métricas de auditoria derivam de violações citadas, nunca de números livres
  • Dados legados migrados e conferidos
  • 6 artifacts republicados sem perda de db/assets
  • Tarefa local desligada sem período de sobreposição
  • Backup restaurado com sucesso ao menos uma vez
  • Nenhum segredo no repositório; boot falha se faltar segredo obrigatório
